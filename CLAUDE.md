# Drawably for SwiftUI — working notes

A SwiftUI port of the web library [Drawably](https://www.drawably.dev)
(MIT, © 2026 Daniel Belyi). Its twin is
[drawably-android](https://github.com/dim971/drawably-android); the two are kept
in step deliberately.

## The one rule that matters

**The engine's output is pinned to the JavaScript original, byte for byte.**

`Tests/DrawablyTests/Fixtures/goldens.json` is generated from the published npm
package. The tests rebuild each case through the Swift engine and compare
strings. There is no tolerance and there is not meant to be one.

If a golden fails, the port has drifted — find out why. Do not widen anything,
do not regenerate the fixtures to make a failure go away. Regenerating is only
correct when deliberately tracking a new upstream version, and the diff should
be explainable.

Two places already needed care to get there, both documented in
`docs/fidelity.md`:

- `jsToFixed2` reproduces `Number.prototype.toFixed(2)`, which rounds exact
  halves away from zero where `%.2f` rounds to even.
- Sample counts come from `ceil(length / step)`, so a last-ulp difference in
  `cos`/`sin`/`atan2`/`hypot` can add a point and desynchronise every later PRNG
  draw. Darwin currently agrees with V8; the Kotlin port had to force fdlibm.

## Layout

```
Sources/Drawably/
  Core/         pure maths — PRNG, sampling, jitter, shapes. No UI types.
  Theme/        DrawablyTheme and its environment key
  Sketch/       layer geometry, roles, the renderer, seeds, tilt
  Components/   the fifteen controls
Tests/          goldens, formatting, button wash, tilt
Showcase/       the catalog app (project generated by XcodeGen, not checked in)
Tools/          gen-goldens.mjs, gen-icon.mjs — Node, run by hand
```

`docs/architecture.md` explains how a sketch reaches the screen.

## Conventions worth keeping

- **Zero warnings.** Package and showcase, on the release Xcode *and* the
  current beta. Check both with `DEVELOPER_DIR`.
- **Generate geometry once.** `SketchChrome` builds the boil frames per box
  size, seed and options and caches them. Nothing is generated in a draw pass.
  Presentation state — trim, offset, scale, visibility, fill — is *not* part of
  the cache key, so touching a control redraws it rather than regenerating it.
- **The sketch carries no semantics.** Every control wraps a real SwiftUI
  control so VoiceOver, focus and keyboard keep working. That is the point of
  the original and it should stay true here.
- **Seeds are the reproducibility handle.** Anything about how something is
  drawn should be discussed with a pinned seed.
- Comments explain why, not what. If a constant looks arbitrary, say where it
  came from.
- `docs/coding-style.md` is the style contract. Note in particular that `Core`
  and `LayerGeometry` keep upstream's positional signatures deliberately — do
  not "fix" them into idiomatic argument labels.

## Verifying

```sh
make test                                  # goldens
make lint                                  # swiftformat --lint, swiftlint
make showcase                              # build and run in the simulator
DEVELOPER_DIR=/Applications/Xcode-<beta>.app/Contents/Developer swift build --build-tests
```

Screenshots: `xcrun simctl io booted screenshot out.png`.

A note from experience: synthetic clicks posted with `CGEvent` reach the
simulator and drive `onTapGesture`, but do **not** drive SwiftUI `Button`s. When
you need to see a pressed or presented state, prefer a pure function you can
unit-test, or temporarily force the state and screenshot it — do not conclude
from a non-reacting `Button` that the feature is broken.

## Staying in step with Android

A change to shared behaviour — geometry, theming, a control's states, a new
modifier — should land in both repositories. The Kotlin port mirrors this
structure file for file, and both replay the same `goldens.json`.
